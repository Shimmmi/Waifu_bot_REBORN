**Версия:** 1.0

## 0. Важная оговорка

Как и с экраном «Совершенствование» — у меня нет исходного HTML/CSS этого экрана, только скриншот. Ниже целевая спецификация и контракт данных, а не диф по строкам существующего файла.

Этот экран не значится в списке основных страниц исходного ТЗ проекта (`profile.html`, `dungeons.html`, `shop.html`, `tavern.html`, `caravan.html`, `training_hall.html`, `guild_hall.html`, `settings.html`, `waifu_generator.html`) — по всей видимости, это стартовая точка входа в Mini App (загружается первой, до `profile.html`).

**Шаг 0 для Cursor:**

1. Найти реальный файл поиском по уникальным строкам:
   ```
   grep -rn "Продолжить" webapp/
   grep -rn "WAIFU REBORN\|Waifu Reborn" webapp/
   ```
2. Проверить, как Telegram-бот открывает Mini App (`WebAppInfo(url=...)` в коде бота на aiogram) — какой файл отдаётся как точка входа. Это, скорее всего, и есть искомый экран.
3. Проверить ветвление для новых игроков: по исходному ТЗ проекта «при первом запуске бота открывается страница создания ОВ (`waifu_generator.html`)» — то есть этот экран, возможно, показывается **только вернувшимся игрокам**, у которых уже есть персонаж. Уточнить фактическую логику роутинга у бэкенда/в текущем коде, прежде чем менять что-либо в условиях показа.

Новые CSS-классы ниже — с префиксом `mm-`, чтобы не столкнуться с общим `styles.css` (там уже используются достаточно общие имена вроде `.menu`, `.btn`, которые легко случайно перекрыть).

## 1. Дизайн-токены и шрифты

Переиспользовать один в один блок токенов из ТЗ по dungeons.html (раздел 2) и paragon-редизайну (раздел 2) — не дублировать переменные, подключить эту страницу к тому же файлу токенов/бандлу. Для самодостаточности:

```css
body.page-mainmenu {
  --ink:#0a0705; --panel:#1b130c; --panel-2:#241a10;
  --parchment:#ecdfc6; --parchment-dim:#9c8b76; --parchment-faint:#6b5c4b;
  --gold:#e2a93f; --gold-bright:#ffd97a;
  --ember:#e2543f; --ember-bright:#ff8a65;
  --rune:#49c9b3; --rune-bright:#7ff0dd;
  --line:rgba(226,169,63,.22);
  --font-display:"Cinzel", serif;
  --font-body:"Manrope", system-ui, -apple-system, "Segoe UI", sans-serif;
  --font-hud:"Rajdhani", var(--font-body);
}
```

**Это самый нагруженный по перформансу экран из всех трёх редизайнов** — он рендерится первым, до входа в игру, и от его скорости прямо зависит retention (первое впечатление + время до интерактивности). Это усиливает то, что уже было отмечено в ТЗ по dungeons.html (раздел 3): шрифты — самохостинг WOFF2 с `font-display: swap`, никакого блокирующего `<link>` на Google Fonts на критичном пути. Здесь это не «желательно», а обязательно: на splash-экране лишний внешний RTT ощущается сильнее всего, потому что больше вообще ничего не происходит, пока не отрендерился текст логотипа.

## 2. Декоративный фон — сознательно без растровой иллюстрации

В брифе было прямо сказано, что арт-иллюстрация будет заменена, поэтому в концепте фон собран из CSS/SVG (лучи, боке, лепестки, line-art силуэт крыльев), без единого файла изображения. **Рекомендация: сохранить именно такой подход даже после того, как появится финальный арт**, по двум причинам:

1. Декоративный слой (лучи/лепестки/боке) не зависит от арта и не потребует правок при каждой смене иллюстрации.
2. Если поверх всё же добавляется растровая иллюстрация персонажей — это должен быть **один** оптимизированный WebP/AVIF на задний план (не несколько PNG слоями, как в оригинальном скриншоте, где видно per-character вырезки), с `loading="eager"` и `fetchpriority="high"`, и обязательно с указанным `width`/`height` (или `aspect-ratio` в CSS), чтобы не было CLS (сдвига layout) в момент подгрузки — на splash-экране это особенно заметно, потому что пользователь смотрит именно в эту область.

```html
<!-- если/когда добавляется финальная иллюстрация -->
<img class="mm-bg-art" src="/webapp/assets/menu/hero-art.webp" alt=""
     width="750" height="1200" loading="eager" fetchpriority="high" />
```

`alt=""` — иллюстрация чисто декоративная, не несёт информации, не должна зачитываться скринридером.

**Анимированные декоративные слои — бюджет производительности.** Вращение лучей (`.mm-bg-sunburst`, 90s linear infinite), парящее боке и падающие лепестки — это `transform`/`opacity`-анимации (не layout-триггерящие), в целом дёшево, но на слабых Android-устройствах внутри Telegram WebView (а это заметная доля аудитории Telegram-ботов) 10 одновременных CSS-анимаций на первом экране — ощутимая нагрузка. Рекомендация:

- Ограничить число одновременных лепестков 6–8 (в макете 10, для реального прода можно срезать).
- Проверить на реальном low-end устройстве (или через CPU throttling в DevTools ×4–×6) — если есть просадка FPS в момент открытия, лепестки — первое, что можно убрать/проредить, они наименее значимый декоративный элемент.
- `prefers-reduced-motion: reduce` уже отключает все анимации через общее правило в токенах — сохранить этот блок при переносе.

## 3. Telegram Mini App — интеграционные особенности этого экрана

Этого не было ни у dungeons, ни у paragon-страницы (они уже «внутри» игры), но критично для стартового экрана:

### 3.1 Высота вьюпорта

`100dvh`, использованный в макете, не всегда точно совпадает с реальной высотой Telegram WebView (там своя шапка/чат-подложка, плюс `Telegram.WebApp.expand()` меняет доступную высоту динамически). Рекомендация:

```js
// в реальной интеграции — подписаться на изменение вьюпорта Telegram,
// а не полагаться только на CSS dvh
Telegram.WebApp.ready();
Telegram.WebApp.expand();
const applyViewportHeight = () => {
  document.documentElement.style.setProperty('--tg-vh', Telegram.WebApp.viewportStableHeight + 'px');
};
Telegram.WebApp.onEvent('viewportChanged', applyViewportHeight);
applyViewportHeight();
```
```css
.mm-screen{ height: var(--tg-vh, 100dvh); }
```

### 3.2 Кнопка «Продолжить» — нативный MainButton или кастомная кнопка?

Telegram Mini Apps предоставляет нативный `Telegram.WebApp.MainButton` — многие боты используют его для главного CTA вместо HTML-кнопки. **Рекомендация: оставить кастомную HTML-кнопку**, а не переключаться на нативный MainButton — у него нет градиентной заливки, sheen-анимации и корнер-скобок, то есть переход на него потерял бы весь визуальный апгрейд этого ТЗ. Нативный `MainButton` стоит держать в уме для **других**, более простых экранов (например, подтверждений), но не здесь.

`Telegram.WebApp.BackButton` — уточнить, должен ли он показываться на этом экране (скорее нет, это точка входа, возврата отсюда никуда нет) или должен появляться, если пользователь попал сюда через «Профиль» → назад.

### 3.3 Тактильный отклик

Telegram даёт `HapticFeedback` бесплатно — стоит использовать на всех тапах по кнопкам меню, это дешёвый способ усилить ощущение «сочности», к которому и так стремится этот редизайн:

```js
document.querySelectorAll('.mm-menu-btn, .mm-icon-btn').forEach(el => {
  el.addEventListener('click', () => {
    Telegram.WebApp.HapticFeedback.impactOccurred('light');
  });
});
```

### 3.4 Тема Telegram

`Telegram.WebApp.themeParams` даёт цвета текущей темы пользователя (тёмная/светлая, акцентный цвет клиента). Экран сознательно **не подстраивается** под эти цвета (у игры собственный golden dark-fantasy брендинг, не системная тема Telegram) — это осознанное решение, но стоит явно задать `Telegram.WebApp.setHeaderColor()`/`setBackgroundColor()` под `--ink`, чтобы системная рамка вокруг WebView (если видна) не контрастировала с игровым фоном.

## 4. Компоненты

### 4.1 `.mm-top-bar`

```html
<div class="mm-top-bar">
  <button class="mm-icon-btn" id="soundBtn" aria-label="Звук" aria-pressed="true">🔊</button>
  <div class="mm-version-tag" id="versionTag">v1.0.3</div>
  <button class="mm-icon-btn" id="settingsBtn" aria-label="Настройки">⚙</button>
</div>
```

**Данные:** `versionTag` — из билд-системы (например, инжектится при сборке фронта, не хардкодить). `soundBtn` — persisted-состояние (реальное хранилище настроек пользователя на бэкенде/в Telegram CloudStorage — **не** `localStorage`, он ненадёжен внутри Telegram WebView на части клиентов). `settingsBtn` — уточнить: ведёт в `settings.html` или открывает модалку тут же.

### 4.2 `.mm-logo-wrap`

Чисто декоративный, статичный текстовый блок, без завязки на данные — как есть в макете. Единственное, что может понадобиться — версия локализации, если у игры будет не только русский (пока не актуально).

### 4.3 `.mm-menu-actions`

```html
<div class="mm-menu-actions">
  <div class="mm-daily-chip" id="dailyChip"><span class="lbl">🎁 Награда дня доступна</span><span class="dot"></span></div>
  <button class="mm-menu-btn primary" id="btnContinue"><span class="ico">▶</span><span class="lbl">Продолжить</span></button>
  <button class="mm-menu-btn secondary" id="btnProfile"><span class="ico">🧝</span><span class="lbl">Профиль</span></button>
  <button class="mm-menu-btn secondary" id="btnInfo"><span class="ico">ℹ</span><span class="lbl">Информация</span></button>
</div>
```

**Контракт данных / состояния:**

| Элемент | Источник | Поведение |
|---|---|---|
| `#dailyChip` | `hasClaimedDailyReward: boolean` | Если `true` — либо скрыть чип, либо сменить текст на «Награда получена» и убрать пульсирующую точку. Сейчас в CSS точка (`.dot`) всегда анимирована — это должно означать «доступно», не «есть новости вообще». |
| `#btnContinue` | состояние сессии | Текст/иконка может меняться: `"Продолжить"` для игрока в процессе, но если это всё-таки первый экран для части новых пользователей (см. п.0.3) — понадобится вариант `"Начать"` без иконки ▶ паузы. |
| `#btnProfile`, `#btnInfo` | — | Прямая навигация, доп. состояний не требуют. |

**Важно:** в макете клик по кнопкам показывает демо-тост («Продолжаем ваше приключение…» и т.д.) — это заглушка для превью. В реальной реализации клик должен **сразу вызывать переход** (роутер/смена страницы), а не показывать тост поверх текущего экрана. Тост-компонент (`#toast`) можно оставить в общей библиотеке компонентов для других сценариев (лёгкие уведомления в игре), но не как реакцию на нажатие этих трёх кнопок.

### 4.4 `.mm-bottom-bar`

```html
<div class="mm-bottom-bar">
  <a class="mm-social-link" href="https://t.me/<канал>" target="_blank" rel="noopener">✈️ Наш канал</a>
  <span class="mm-copy">© Waifu Reborn · 2026</span>
</div>
```

**Уточнить:** реальный URL Telegram-канала/чата проекта (в макете плейсхолдер `#`). Открытие внешней ссылки из Mini App — использовать `Telegram.WebApp.openTelegramLink()` вместо обычного `<a href>`, чтобы переход происходил нативно внутри Telegram, а не пытался открыть системный браузер:

```js
document.querySelector('.mm-social-link').addEventListener('click', (e) => {
  e.preventDefault();
  Telegram.WebApp.openTelegramLink('https://t.me/<канал>');
});
```

## 5. QA-чеклист

- [ ] Первая отрисовка (логотип + кнопки видны и интерактивны) укладывается в комфортное время на среднем Android-устройстве внутри Telegram WebView — не завязано на внешние шрифт-запросы, если самохостинг ещё не внедрён.
- [ ] `Telegram.WebApp.viewportStableHeight` корректно применяется, экран не обрезается и не оставляет пустую полосу снизу при разных высотах клавиатуры/чата у разных пользователей.
- [ ] Логика показа экрана — новый игрок не залипает здесь вместо `waifu_generator.html` (см. п.0.3), возвращающийся игрок не видит его пропущенным.
- [ ] `#dailyChip` корректно отражает реальное состояние (получено/не получено), не показывает пульсацию, если награда уже забрана.
- [ ] Тактильный отклик (`HapticFeedback`) не дублируется и не падает с ошибкой на клиентах без поддержки (Telegram Desktop/Web, где часть нативных методов no-op — обернуть в try/catch или проверку `Telegram.WebApp.isVersionAtLeast(...)`).
- [ ] Внешняя ссылка на канал открывается через `openTelegramLink`, не через обычный `<a>` (иначе на части платформ уводит из Mini App в системный браузер).
- [ ] `prefers-reduced-motion: reduce` отключает лепестки/боке/спиннер лучей/sheen-анимацию кнопки.
- [ ] Проверить на реальном low-end устройстве — при просадке FPS в первую очередь сократить количество `.mm-petal`.
- [ ] Клавиатурный фокус (`:focus-visible`) виден на всех кнопках — актуально прежде всего для Telegram Web-версии (там реально используют Tab).
- [ ] `alt=""` на декоративной иллюстрации (если/когда добавится растровый арт), логотип-текст остаётся настоящим текстом (не картинкой) для читаемости скринридером и на случай локализации.

1. **Токены + шрифты + перф-база** (разделы 1–2). Самохостинг шрифтов, если ещё не сделан для dungeons.html — сделать один раз на всё приложение, не только для этого экрана.

4. **Подключение данных** (daily-chip, версия сборки, ветвление «Продолжить» vs «Начать») — требует уточнений из раздела 7.
